## 一、项目概述

### 1.1 产品定位

> **project-doc：嵌入 AI 编程工作流的轻量级文档归档与任务追踪工具**

一句话价值主张：
> "让文档不再散落，让变更可追溯，让 AI 帮你管理项目"

### 1.2 目标用户

**个人开发者**——独立开发者、自由职业者，需要简单易用的文档管理工具。

### 1.3 商业目标

**阶段目标**：先积累用户和口碑，盈利模式后续探索。

## 二、市场分析

### 2.1 AI 编程助手插件市场现状

**市场特征**：
- **新兴阶段**：AI 编程助手（Claude Code、GitHub Copilot、Cursor 等）正在快速普及，但插件生态尚未成熟
- **窗口期**：各平台正在建立插件体系，早期入驻者有机会获得官方推广和用户先发优势
- **用户痛点普遍**：文档混乱、需求追溯缺失是开发者的共性痛点，但现有解决方案（Jira、Notion）太重或与 AI 工具割裂

**竞争格局**：
- **重型工具**：Jira、Confluence、Notion —— 功能强大但学习成本高，与 AI 编程助手无集成
- **轻量工具**：Obsidian、Logseq —— 个人笔记友好，但缺乏项目文档规范和任务追踪
- **AI 插件**：目前各平台插件市场以 MCP servers、代码生成工具为主，**文档管理类插件几乎没有**

**机会点**：
> project-doc 处于 **"AI 编程助手 + 文档管理" 的空白交叉领域**，有机会成为该细分市场的先行者。

### 2.2 核心差异化优势（五维组合）

| 维度 | project-doc | 传统工具对比 |
|------|-------------|--------------|
| **AI 集成** | 直接嵌入 Claude Code/Codex 工作流，无需切换工具 | Notion/Obsidian 需独立打开，与编程环境割裂 |
| **规范化** | 强制目录分类、命名规范、DOC_INDEX 入口 | 自由放置，易混乱 |
| **变更追溯** | 自动关联 commit、任务状态、需求变更 | 手动记录或无追溯 |
| **轻量简洁** | Markdown 文件，无数据库，无云依赖 | Jira/Confluence 需登录、配置、学习 |
| **多平台** | Phase 3 将支持 Cursor、OpenCode 等 | 传统工具与 AI 编程助手无原生集成 |

**核心护城河**：
组合优势形成的"小而美"壁垒——单一功能容易被替代，但"AI 集成 + 规范 + 追溯 + 轻量"的组合难以被快速复制。

## 三、推广策略

### 策略框架：开发者口碑优先 + 开源社区建设（全球市场）

### 3.1 GitHub 展示优化（发布前准备）

**目标**：让全球开发者在 30 秒内理解价值并决定试用

**关键动作**：
| 优化项 | 具体内容 |
|--------|----------|
| README 开篇 | 痛点共鸣 + 一句话价值主张 + 快速上手 Demo |
| 动态演示 | GIF/视频展示 `/project-init` 和 `/req-change` 的使用效果 |
| 对比表格 | 与 Notion、Jira、Obsidian 的对比，突出差异化 |
| 徽章展示 | License、Version、Platform 支持、Downloads |
| 示例项目 | 提供一个 mini 项目展示完整文档结构 |
| 多语言支持 | README 英文为主，中文版作为 README-zh.md |

### 3.2 首次发布公告（全球发布）

**目标**：在核心开发者社区获得首次曝光

**全球渠道优先级**：
| 渠道 | 发布内容 | 预期效果 |
|------|----------|----------|
| Hacker News | "Show HN: A doc tracker that embeds into AI coding assistants" | 高质量全球开发者关注 |
| Reddit | r/programming, r/opensource, r/claudeai 等子版块 | 多元开发者社区讨论 |
| Twitter/X | 简短介绍 + 演示截图，使用 #opensource #AIcoding 标签 | 快速全球传播 |
| Product Hunt | 新产品发布平台，科技圈关注度高 | 获得产品爱好者关注 |
| Dev.to | 开发者博客社区，发布完整故事 | 深度内容传播 |
| GitHub Discussions | 正式发布公告，收集反馈 | 全球用户互动入口 |
| Discord 服务器 | Claude Code、Cursor 等社区服务器分享 | 直接触达 AI 编程用户 |

**公告内容策略**：
- 讲真实故事而非产品介绍："My requirement docs were scattered everywhere, every change was untraceable..."
- 突出开源 + 开发者友好：Open source, lightweight, 5-minute setup
- 强调跨平台愿景：Currently for Claude Code, coming to Cursor, Codex, and more
- 邀请 Early Adopter：Welcoming feedback, contributions, and community building

### 3.3 内容营销（持续运营）

**目标**：建立技术博客，持续输出有价值内容

**全球内容主题规划**：
| 主题 | 示例标题 | 目的 |
|------|----------|------|

| 开源故事 | "From Pain Point to Open Source: My Journey Building project-doc" | 建立情感连接 |

**全球发布平台**：
- GitHub Pages 博客（个人技术博客，SEO 友好）
- Medium（全球开发者聚集，易传播）

| 渠道 | 用途 |
|------|------|
| GitHub Issues | Bug 报告、功能请求 |
| GitHub Discussions | 问答、经验分享 |

**版本号规范（SemVer）**：
| 版本类型 | 含义 | 示例 |
|----------|------|------|
| 0.x.x | 开发阶段，API 可能不稳定 | v0.1.0 → v0.2.0 |

## 五、未来盈利模式规划

> 注：当前阶段聚焦用户积累，以下盈利模式为**未来探索方向**，暂不执行。

### 5.1 可能的盈利路径

| 模式 | 适用场景 | 启动时机 | 收入潜力 |
|------|----------|----------|----------|
| A. 云服务增值 | 提供云端文档同步、备份、协作功能 | 用户量 > 1000，有协作需求反馈 | 中等（订阅制 $5-15/月） |
| B. 企业定制服务 | 为企业客户定制规则、模板、私有部署 | 有企业用户主动咨询 | 较高（一次性 + 维护费） |
| C. Pro 版功能 | 多项目管理、高级分析、团队协作功能 | 个人版用户量大，有付费需求反馈 | 中等（订阅制 $9-29/月） |
| D. 培训/咨询 | 文档方法论培训、团队落地咨询 | 社群活跃，方法论有影响力 | 低-中等（按项目收费） |
| E. 赞助/捐赠 | GitHub Sponsors、Open Collective 接受用户赞助 | 用户认可度高，愿意支持 | 低（不稳定） |

### 5.2 推荐的盈利探索顺序

```
阶段 1（当前）: 完全免费，积累用户和口碑
    ↓ 用户量 > 500，有真实使用案例
阶段 2: 开放 GitHub Sponsors（接受自愿赞助）
    ↓ 用户量 > 1000，收到企业/团队咨询
阶段 3: 评估企业定制服务或 Pro 版功能
    ↓ 用户量 > 5000，协作需求明确
阶段 4: 启动云服务或 Pro 版（如果市场验证通过）
```

### 5.3 盈利模式评估标准

在考虑启动任何盈利模式前，需验证以下条件：

| 条件 | 验证方法 |
|------|----------|
| 用户量达标 | GitHub Downloads/Stargazers > 目标阈值 |
| 付费意愿存在 | 用户主动询问付费功能、企业客户咨询 |
| 差异化明确 | 免费版功能清晰，付费版有不可替代价值 |
| 竞品分析 | 确认定价不高于竞品、功能有优势 |
| 成本可控 | 云服务/维护成本低于预期收入 |

### 5.4 不推荐的盈利方式

| 方式 | 不推荐原因 |
|------|------------|
| 一次性买断 | 持续迭代的产品不适合买断模式 |
| 广告植入 | 开发者工具嵌入广告会损害体验和信任 |
| 核心功能收费 | 会限制用户增长，违背先积累用户的目标 |
| 过早订阅制 | 用户量不足时，订阅制维护成本高 |
